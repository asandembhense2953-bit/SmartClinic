CHALLENGES & HOW THEY WERE RESOLVED
════════════════════════════════════════════════════════════

Challenge 1: Supabase join syntax
  The Supabase JS client uses a different syntax for joins
  compared to raw SQL. Resolved by reading the Supabase docs
  and using the select('*, relation(fields)') pattern.

Challenge 2: Preventing double check-in
  Identified early that the queue needed a uniqueness check
  before Sprint 2. Added getByAppointment() to the Queue
  model to detect existing active entries.

Challenge 3: 3NF for consultation timing
  Initially planned to store consult_start/end on the
  appointments table, but this would create a partial
  dependency. Moved timing fields to queue_entries to
  maintain 3NF compliance.


════════════════════════════════════════════════════════════
LESSONS LEARNED
════════════════════════════════════════════════════════════
- Designing the ERD before writing any code saved significant
  refactoring time. We recommend always starting with the
  schema.
- Supabase's real-time features were not needed for this
  sprint but will be considered for Sprint 2 as an
  alternative to polling.
- The MVC split made it easy to add new entities — the
  pattern was consistent across patients, doctors, and
  appointments.
